# 어떤 분리배출 질문에 답할 수 있는가

## 사용자의 일과 오답 위험

주 사용자는 주민 문의에 답하는 안내 담당자입니다. 주민이 “이거 언제 내놔요?”라고 물으면 품목, 자치구, 필요에 따라 동·주택 유형을 확인합니다. 이어 공통 품목사전과 해당 구청의 안내에서 적용 조건과 날짜를 대조한 다음 근거 링크를 전달합니다. 문구가 비슷한 이웃 구의 규칙을 가져오거나 기간이 겹치는 안내 중 하나를 임의로 택하면, 검색 결과가 그럴듯해도 잘못된 안내가 됩니다.

| 실제로 마주치는 질문 | 에이전트가 해야 할 일 | 확인할 증거 |
| --- | --- | --- |
| “서대문구인데 생활쓰레기는 언제 내놓나요?” | 동별로 기준이 갈리고 동을 알려주지 않았다면 동을 되묻습니다. 받은 조건으로 같은 질문을 다시 검색합니다. | 최초·추가 요청, 선택한 구와 동, 답변에 사용한 원문 구절 |
| “마포구 안내에서 같은 기간에 두 시간이 보이는데 어느 쪽인가요?” | 원문에서 적용 조건을 확인하고 충돌이 해소되지 않으면 시간을 확정하기 어렵다고 안내합니다. | 충돌한 두 구절의 위치, 확인일, 보류 사유 |
| “이 품목은 어떻게 분리하나요?” | 공통 품목 지침으로 답할 수 있는 부분을 설명합니다. 지역 일정이 필요해지면 해당 구의 별도 근거를 찾습니다. | 품목 근거와 지역 근거의 문서 ID, 실제 인용 청크 |

이 사례들은 구현·평가 설계를 위한 예시입니다. 실제 답변에 쓸 규칙은 수집 시점의 원문으로 확인합니다. RAG를 선택한 이유는 안내 근거가 여러 기관 문서에 있고 적용 조건과 문구가 바뀔 수 있기 때문입니다. 팀 범위는 서울 25개 구, 대표 품목 3~5개, 일괄 수집입니다. 장소 조회와 정기 갱신은 후속 범위이며 실제 민원 처리·배출 신청·모델 학습은 수행 범위 밖입니다.

## 같은 질문으로 무엇을 비교하는가

수업 과제는 BM25와 벡터 검색의 결합, 별도 재정렬, 최적화 한 가지, 고정 평가를 요구합니다. 아래 RRF와 정확 일치 캐시는 팀이 채택 여부를 첫날 확정할 **제안**입니다. 품질을 우선하고, 근거와 답변 품질이 비슷한 구성끼리 지연과 호출 비용을 비교합니다. 팀 시연용 목표값은 [로드맵](../ROADMAP.md)에 있습니다. 수업 비교 지표의 목표값도 결과를 보기 전에 합의해 설정 버전과 함께 기록합니다. 기존 업무 소요시간은 아직 측정하지 않았습니다.

| 구성 | 같은 문서·질문에서 달라지는 부분 | 남길 원본 |
| --- | --- | --- |
| A · Vector | 임베딩 유사도로 후보를 검색합니다. | 임베딩 모델·차원, 검색 개수, 청크 ID·점수·순위 |
| B · Hybrid | 동일 청크에 BM25와 Vector를 각각 실행합니다. 제안 방식인 RRF는 각 목록의 순위로 결합해 서로 단위가 다른 점수를 다룰 수 있습니다. | 두 후보 목록, 후보 수, 결합 상수·가중치, 청크 ID 기준 중복 제거 결과 |
| C · Hybrid + 재정렬 | B의 후보를 질의–청크 쌍으로 다시 평가합니다. 선택한 구와 적용 조건을 지키면서 최종 순위를 만듭니다. | reranker 모델 또는 방식, 입력 수, 재정렬 전후 순위와 점수 |

A/B/C는 동일한 문서·색인 버전, 조건 필터, 생성 모델, 프롬프트, 생성 한도와 컨텍스트 예산을 사용합니다. 각 구성은 **평가용 상위 5개**까지 기록하고, 그중 **상위 3개**를 답변·화면에 전달합니다. 후보가 적으면 실제 개수를 유지합니다. 검색 점수는 질의 관련도 지표이며 안내가 사실일 확률로 표시하지 않습니다.

**최적화 제안 · 정확 일치 캐시.** 같은 FAQ가 반복될 때의 지연과, 원문 변경 후 낡은 답이 재사용될 위험을 함께 볼 수 있습니다. 최종 응답 캐시 키에 원질문, 구·동·주택 유형, 사용 범위, 문서·색인·모델·프롬프트·검색 설정 버전을 포함합니다. 버전 변경 시 기존 키를 무효화하고 오류 응답은 저장하지 않습니다. A/B/C 비교에서는 캐시를 끕니다. 별도로 고정한 답변 가능 질문 5개에 대해 최초 미적중·동일 질문 적중·색인 버전 변경 후 미적중을 실행해 총 15건의 결과와 인용을 보관합니다. 팀이 쿼리 리라이트를 택하면 C와 C+리라이트를 동일 최종 20문항으로 비교하고 원질문·변환문·실패 시 원질문 복귀·추가 지연을 기록합니다.

## 두 평가표를 읽는 방법

| 구분 | 문항과 판정 | 사용 시점 |
| --- | --- | --- |
| 팀 시연 인수 | 구별 기본 25건과 품질 16건. 지역 혼입, 상위 3개 근거, 추가 질문·보류·출처 화면을 검증합니다. | 개발·통합 중 반복. 팀 목표와 실제 수치를 구분합니다. |
| 수업 개발셋 | `eval/dev.json` 10문항. 답변 가능 8개와 근거 없음 2개입니다. | 청킹·검색·근거 부족 판정 조정에 사용합니다. |
| 수업 최종셋 | `eval/test.json` 20문항. 직접 검색 10개, 표현 변형·유사 조건 7개, 근거 없음 3개입니다. A/B/C 각 1회로 기본 60건입니다. | 문항 ID와 설정을 고정한 후 실행합니다. 팀 시연·튜닝에서 이미 사용한 질문은 제외합니다. |

개발·최종을 합쳐 서로 다른 답변 가능 질문 25개를 공식 문서로 뒷받침합니다. 유사 단어나 예외 조건 때문에 혼동하기 쉬운 문서도 2개 이상 선정합니다. 문항에는 ID·유형·질문·필수 사실·허용 청크·원문 위치를 둡니다. 근거 없는 문항은 근거 ID를 비우고 부재 판정 이유를 씁니다. 색인에는 원문만 넣고 정답표는 검색·생성 입력에서 분리합니다. 청킹 변경 시 근거 매핑을 갱신하고 최종 실행 전에 버전을 다시 고정합니다.

- **검색**은 답변 가능 17문항에서 허용 근거가 상위 5개에 하나라도 든 건수로 Hit@5를 계산합니다. 분모는 17이며 검색 실패는 0입니다.
- **답변**은 필수 사실 충족 건수와 인용 적합 건수를 각각 17로 나눕니다. 근거 없는 문항은 올바르게 보류한 건수를 3으로 나눕니다. 호출 오류는 보류 성공으로 세지 않습니다.
- **운영**은 성공 호출 수/전체 시도, 성공 요청 전체 지연의 평균·중앙값·표본 수, 오류·타임아웃 수를 남깁니다. 비용 비교에는 사용량이나 호출 횟수 등 산출 근거를 붙입니다.

## 팀원이 남길 증거와 읽을 순서

1. **수집 담당자**는 문서 ID·제목·공식 URL·이용 조건·수집일·원문 위치를 목록화합니다. 외부 모델 전송 가능 여부도 확인합니다. 각 청크에는 안정적인 ID·문서 ID·페이지나 절·행 또는 원문 발췌를 보존합니다.
2. **검색·생성·평가 담당자**는 실행 ID·질문 ID를 공통 키로 사용합니다. `results/`에 구성별 후보·점수·순위, 문서/색인/모델/프롬프트 버전, 답변 원문·인용·시간·상태·채점 사유를 기록합니다. 실패·재시도·추가 실험은 식별할 수 있게 남깁니다. 오답을 보면 먼저 정답 청크가 후보에 들어왔는지, 다음으로 순위·생성·인용 중 어디에서 실패했는지 살펴봅니다.
3. **통합·화면 담당자**는 [API 계약](TEAM-SETUP.md)으로 상태와 인용을 대조합니다. **다른 팀원**이 README를 따라 색인을 재생성하고 정상·근거 없음·최적화 사례를 재실행합니다. 최종 구성과 한계는 `report.md`, 팀원별 코드·검증·리뷰 링크는 `contributions.md`에 모읍니다. 이 경로들은 구현 이후 작성할 산출물입니다.
